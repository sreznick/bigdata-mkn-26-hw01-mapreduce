# Задание 3. Подозрительные пары переводов за соседние сутки

## Запуск

```bash
python task3/task3.py transactions.csv > result.csv              # inline
python task3/task3.py -r local part1.csv part2.csv               # несколько процессов
python task3/task3.py -r hadoop hdfs:///path/to/input -o hdfs:///path/to/output
```

Выход — по одной строке на подозрительную пару, без заголовка:

```csv
user_id,transaction_id_1,transaction_id_2,total_amount
```

## Идея решения

Пара может состоять только из переводов одного клиента, поэтому ключ — `user_id`.

- **Маппер** выдаёт `user_id → [номер дня, transaction_id, amount]`, где номер дня —
  `date.fromisoformat(timestamp[:10]).toordinal()`, порядковый номер календарной даты.
  Соседние сутки — это просто `day` и `day + 1`, переходы через месяц, год и 29 февраля
  учитываются автоматически.
- **Reducer** раскладывает переводы клиента по дням в словаре и для каждого дня `d`, у которого есть
  день `d + 1`, перебирает пары «перевод из `d`» × «перевод из `d + 1`». Переводы каждого дня
  отсортированы по убыванию суммы, поэтому как только сумма пары стала `≤ T`, внутренний цикл
  прерывается — дальше суммы только меньше.

Каждая пара получается ровно один раз, первым в ней идёт перевод с более ранней датой.
Пары внутри одного дня и через день не рассматриваются.

### Почему без вторичной сортировки и без проблем с памятью

Порядок значений в reducer не важен: группировка по дням делается словарём. В памяти в каждый момент
лежат переводы только **одного** клиента — mrjob вызывает reducer отдельно для каждого ключа и подаёт
значения генератором из отсортированного потока shuffle (`itertools.groupby`). Миллиарды записей на
машине проходят через reducer потоком, а буфер ограничен 1000 переводов (граница из условия).

Вариант с ключом `(user_id, дата)` и отправкой каждого перевода дважды (в свой день и в следующий)
тоже обходится без вторичной сортировки, но удваивает shuffle на 10 млрд строк, поэтому не выбран.

### Точность

Суммы и сравнение с порогом считаются в `Decimal`, а не во float. Например, для
`5000 + 5000.0000000000001` float даёт ровно `10000.0` и пара теряется, а точная сумма больше порога.
`total_amount` выводится через `format(total, "f")`: `11000`, `11000.75`, без экспоненты.

## Решения по неоднозначностям условия

- **Соседние сутки** — это календарные даты, а не 24 часа: `23:59:59` и `00:00:00` следующего
  дня — соседние, `00:00` и `23:59` следующего дня — тоже.
- **Часовой пояс** не указан, время берётся как есть.
- **Порядок в паре** — сначала более ранний перевод.
- **Заголовок** во входе пропускается, в выходе не пишется.
- **Порог** строгий: сумма ровно 10000 не подозрительна.
