# Задание 2. Обогащение событий категорией доверия устройства

## Файлы

| Файл           | Назначение                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `task2.py`       | join событий (B) со справочником (A)                                                           |
| `build_bloom.py` | ежедневная job: фильтр Блума по справочнику A                                     |
| `bloom.py`       | фильтр Блума, разбитый на шарды; передаётся задачам через `FILES` |

## Запуск

```bash
# раз в сутки, после обновления справочника
python task2/build_bloom.py --capacity 1000000000 --error-rate 0.01 --shards 64 A.csv > bloom.txt

# ежедневно: join с фильтром
python task2/task2.py --bloom bloom.txt A.csv B.csv > result.csv

# без фильтра — тот же результат, но все события идут в shuffle
python task2/task2.py A.csv B.csv > result.csv
```

На Hadoop `build_bloom.py` выдаёт несколько part-файлов — перед передачей в `--bloom`
их нужно склеить в один (`hadoop fs -getmerge`).

Выход — без заголовка:

```csv
event_id,device_id,event_type,trust_category
```

## Почему так

- Справочник (~1 млрд записей) не помещается в память, поэтому map-side join через словарь невозможен —
  нужен **reduce-side join** по `device_id`.
- Но 95% событий относятся к неизвестным устройствам, и гнать их в shuffle незачем.
  Поэтому по справочнику заранее строится **фильтр Блума** (~1.2 ГБ при 1 млрд устройств и 1% ложных
  срабатываний). Он помещается в память маппера и отсекает почти все лишние события до shuffle.
  Справочник обновляется раз в сутки, так что и фильтр достаточно строить раз в сутки.

### `task2.py`

- **Маппер:**
  - строка из A (2 поля) → `device_id, ["A", trust_category]`;
  - строка из B (3 поля) → `device_id, ["B", event_id, event_type]`, но только если `device_id`
    не пустой и (при `--bloom`) есть в фильтре;
  - заголовки обоих файлов пропускаются.
- **Reducer:** включён `SORT_VALUES = True`, поэтому запись справочника (`"A"` < `"B"`) приходит первой.
  Если первым пришло событие, устройства в справочнике нет — все события ключа отбрасываются.
  Иначе события выводятся по одному, без буферизации, так что «горячие» устройства не страшны.
- Фильтр влияет только на объём shuffle, не на результат: ложные срабатывания отсеиваются в reducer.

### `build_bloom.py` и `bloom.py`

Один фильтр на 1.2 ГБ, собранный из частичных фильтров каждого маппера, гонял бы по сети
по 1.2 ГБ с маппера. Поэтому фильтр **разбит на шарды**:

- маппер считает хеш `device_id` и отправляет `[h1, h2]` в шард `h3 % shards`;
- reducer строит фильтр своего шарда размером `capacity / shards` и выдаёт строку
  `shard,num_shards,base64`;
- при проверке ключ по тому же `h3` попадает в тот же шард. Шарда нет в файле — значит, в него не
  попало ни одного устройства, и ответ «нет».

`key_hashes` берёт 24 байта `blake2b` и делит их на три 64-битных числа: `h1`, `h2` для позиций битов
(double hashing: `pos_i = (h1 + i·h2) mod m`) и независимое `h3` для выбора шарда. Встроенный `hash()`
не подходит: он рандомизирован в каждом процессе, а фильтр строится и проверяется в разных процессах.

## Решения по неоднозначностям условия

- `device_id` сравнивается как есть, без нормализации регистра и разделителей MAC-адреса.
- Файлы A и B различаются по числу полей (2 и 3), поэтому их порядок во входе не важен.
- Заголовок в выходе не пишется.

## Ограничения

- Весь справочник A (20 ГБ) всё равно проходит через shuffle при каждом запуске.
- Каждый маппер держит фильтр целиком в памяти.
